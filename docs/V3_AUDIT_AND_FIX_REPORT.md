# AgentRace V3：源码审计、策略重设计与本地验证

日期：2026-09-13。基线：用户本次上传的 `AgentRace-main(1).zip`，不是远程仓库，也不是仅凭此前对话生成的旧版本。
版本性质：**Survival V3 candidate（待官方对局验收的候选版）**。

## 1. 结论与交付范围

这次已实际修改生产代码，新增独立的白天规则子集模拟器，并执行源码回归、真实初始地图对照、生成地图对照、长周期经济连续性、任务检查包与高密度输入测试。

最关键的结论不是“再松开一个经济开关”，而是：**现有策略把有限的角色回合大量花在低效往返，建筑成长路径又在低等级封顶；任务耗时与错误进一步削弱资金；首夜防御和炮手损失随后放大了这些问题。** 最新 Round7 日志不支持将主因简单归结为商店买入失败。

本轮可运行的核心套件 **322 项通过，0 失败、0 错误、0 跳过**。另有 **22 项 HTTP/入口/回调/子进程冻结对照相关测试未执行通过**：当前容器缺真实 Flask，安装尝试受网络/DNS 限制，完整测试入口已实际尝试并失败，原始输出一并交付。没有用伪造 Flask 或 HTTP 模拟冒充真实传输测试。

**这里没有官方裁判引擎、真实机器人 AI、赛事模型或任务判分沙盒。因此不能宣称已经完整验收、已经打满 1300 回合、必定达到某个分数或胜率。** 交付的是经过明确范围本地验证的候选代码，而不是一份已经取得实战新成绩的版本。

## 2. 重新理解题目：真正需要优化什么

### 2.1 不是单纯的“采矿造墙游戏”

比赛一个半场最多 1300 回合，每天白天 70、夜晚 60，共 10 天。白天必须把人物行动转换成矿物、现金、工事和实际交付的升级；夜晚则必须把人物位置转换为真实可用火力。任务提供另一条重要的资金与积分来源。优化目标不是某一个字段最大，而是让这几条链路同时成立。

资料依据：`AI Spec/未来战争_v1.0_比赛全貌_开发整合版.md` 第 97、130–137 行及第 38 节任务积分；补充解释见 `AI Spec/官方材料核对补充.md`。本轮只使用仓内纯文本资料，没有主动读取或上传 `Official/` 中多模态材料。

### 2.2 必须落实到代码的约束

| 约束 | 对设计的直接影响 |
|---|---|
| 地图 41×32、八邻域移动；基地占 2×2 | 寻路和建造不得把基地当成单格；两侧部署需要对应镜像 |
| 三座武器上限，每座建造 25 金币 | 开局 75 金币必须保护建炮预算，不能被无关采购先消耗 |
| 围墙每面 1 石头 | 采集一趟应支持多面墙，单块往返的移动成本过高 |
| 每座武器需要邻近角色操控，一名角色不能同时操控两座 | “造出 3 座炮”不等于“有 3 座炮能射击”；需要角色—武器—站位联合分配 |
| 升级券由人物背包携带并就近使用 | buy、运送、use、下一观察确认必须闭环；不能以发出买单当成已升级 |
| 武器与基地均存在三级成长 | 调度必须产生二升三的真实缺口和采购任务，而不是只在注释中写升级 |
| 同回合行动有合法性与资金限制 | 不把同回合预计卖矿收入提前用于其他买单；保留最终动作校验器 |
| 任务和命令结果跨回合返回 | 减少无效探索与往返模型调用，比单纯增加提示词长度更重要 |

围墙 1 石头依据补充文件“已确认”；武器数值与操控依据整合版第 551–724 行。整合版对“操控武器是否同时占用角色自己的动作”仍标记歧义：本代码继续采取**保守互斥**，即操炮人物同回合不执行其他动作，不把这项策略选择写成已新增确认的规则。

升级满血、复活与背包保留等按已有规格处理。角色生死、道具是否买到、建筑等级是否改变，以后续实际观察为准，不由计划表虚构。`lastRoundRoleActionResults` 只说明动作合法性，尤其不能把 `submitAnswer=True` 当成答案完全正确。

### 2.3 新版的优化顺序

开局先保证建炮；工人采用“批量采石建墙 + 持续采卖现金”的分工；有钱且能完成往返时采购并交付升级；日落前真正腾出位置、完成三人返防；夜晚在角色保命、已持有道具救急和射击之间做选择。后续逐渐补足三炮三级与基地三级，非紧急墙升级后置，避免便宜小额采购长期消耗大额升级资金。

后方紧凑炮位、两处出口、8/12/16/18 面墙目标、药品阈值及各类优先级都是**可检验的策略假设**，不是官方强制规则，也不是已经证明的最优解。

## 4. 从源码定位的根因与修改

### 4.1 单块石头往返：行为合法，但生产率非常差

原附件 `src/agentrace/strategy.py:949–981`：`needed = stones`，只有背包石头少于一面墙成本才继续采矿；采够一块后转去建一面墙。矿点稍远，采矿只需一回合，往返却需要许多回合。

举例只是算术说明：单程 6 步，采 1、造 1，一面墙就至少 14 个动作回合；一次采 8 块，先付一次往返成本，再顺着围墙位置连续建，能显著减少重复走路。实际地图有障碍，不能直接用这个例子当测得收益。

新 `SurvivalPlanner.build_walls()` 保存 quarry/build 阶段与固定批量配额，最多按一趟 8 面墙准备石料。数量受缺墙数、背包空间和完整往返时间约束；采到一块不会自动折返。矿枯竭后重新选矿，不假定目标永久存在。

### 4.2 成长上限写进了计划：不是缺钱才升不上去

原附件 `strategy.py:692–696` 把武器目标固定为前两天 `2/1/1`，第三天后 `2/2/1`。`strategy.py:198–202` 仅针对一级武器生成 `WeaponUpgradeVoucher1`；基地目标在 `strategy.py:190–192` 也是使用一级券升二级。

新版 `service_candidates()` 根据当前观察产生一级升二级和二级升三级缺口。`procure()` 只在当前资金足够且能完成全程时占用人物；`held_delivery()` 只对真实背包道具生成使用动作。目标死亡或升级已被别人完成时，可以重新选择仍匹配券等级的活目标。

### 4.3 多个调度者重复采购、缺钱任务占用工人

新版统一统计全部存活角色持有的同类券及本回合买单，扣减待补缺口，避免两个运送者同时为同一批需求买重复券。批量购买最多三张同类券，但仍受缺口、钱和背包约束。

没有钱时不锁住工人等待“不存在的预算”，而是继续采集、出售。已经买到的券则优先恢复运送链路，不因跨天、原 job 丢失而永久闲置。连续三次观察到 move 没有位置/背包进展时释放旧任务；这是重规划触发器，不保证能消除所有物理堵塞。

### 4.4 炮位、站位和返防不是三个互不相关的问题

新版同时分配互不重复的武器、人物和站位。预测阶段使用静态障碍估算整条回程，执行阶段仍用当前动态占用与本回合移动预约校验。造墙前洪泛检查现有友军是否仍有通向外部的通路，以及武器邻位是否可达；不把临时人物位置误认为永远不能穿过。

最后复跑确实找到一次新版本自身回归：game28、R20 注入 160 金币场景下，空闲开拓者停在另一工人的指定站位 `(9,23)`，直到自己的返防截止才挪走，导致 R70 只有两名炮手可匹配。这不是买东西失败，而是**已经空闲的人没给执行中的队友让位**。

修复为：开拓者无可执行任务、采购或出售时立即回到自己的指定站位，不等自己最后期限。这个场景先保存失败记录，再验证修复后 8 墙、3 座炮、3 名可就位炮手，并把四初始地图×两种资金场景都加入核心闭环回归。

### 4.5 更细的预算优先级必须用长测检验

本轮最早的 1300 步经济连续性测试也真实失败过：最后炮等级 `3/3/2`，基地三级，18 面墙，末期大量墙已升三级，资金却被低价墙券持续花掉。说明“代码里有二升三分支”仍不够，还必须防止优先级饥饿。

最终修复：非紧急墙升级只有在三座武器均三级、基地三级后才入队；受伤墙的修复剂仍允许参加必要维护。药品采购不抢占恰好足够的已可执行大额升级资金。失败记录 `stress_first_failure.log` 被保留，没有只保存最后的绿色输出。

### 4.6 任务提速：减少空转，不伪造答案正确性

新 `task_inspection.py` 在首次探索时一次只读获取当前题目文档、关联 API/规范和明确引用的源文件，限制路径、拒绝 symlink 越界、不扫描无关同级任务，输出有字符预算和截断标志。

新模式提示词鼓励有依据的批量 API 调用、在允许工作区修改源码并运行题目规定的检查命令，避免“每次模型只决定再 cat 一个文件”。不得修改 checker、测试、规范或评分逻辑；题目确实要求 token 时才读取当次 checker 结果，不使用旧题/对手 token。

继续保留 Task R1 的严格解析、来源绑定、候选管理、重复操作限制与干净 stdout 契约。本地已执行检查包的真实临时目录测试，以及命令下一回合成功 stdout 自动提交、失败 stdout 不提交的状态链路测试。**这些证明协议与检查包行为，不证明模型已经能解对所有真实题。** 本版没有声称实现通用确定性任务求解器。

## 5. 新架构与文件职责

```text
src/main3.py：真实 HTTP 入口、端口参数、环境变量选择策略
    → GameSession.handle：锁、请求指纹、缓存、观察更新、事务提交
        → SurvivalPlanner.run
            白天：已持有道具 → 返防约束 → 建炮 → 任务/运输 → 批量建墙/采卖
            夜晚：角色保命/手头道具 → 唯一炮手匹配 → 攻击 → 支援/返位
        → ActionValidator：最终独立合法性检查
        → 原有回合日志 + survival_v3 决策报告
```

`survival.py` 是独立新策略模块，而不是继续向 `main3.py` 塞所有业务。`task_inspection.py` 单独处理任务资料检查。原 `model/actions/memory/defense` 公共基础尽量复用；原 `strategy.py` 保持不变供对照和回滚。

为保留旧模式回归和已有调用者行为，库直接 `GameSession()` 默认仍是 `defense`；**实际 `main3.py` 的两处会话构造明确选择环境变量 `AGENTRACE_STRATEGY`，未设置时为 `survival`。** 不要靠库默认值判断部署用了什么策略，应看启动日志。

## 6. 实际执行的验证及结果

### 6.1 核心回归与完整套件边界

基线离线核心套件 282 项通过；修改后 322 项通过。新增覆盖包括批量采石、预算饥饿、三级升级、跨角色库存扣减、券真实交付、背包满/资源缺失、角色死亡与目标替换、堵路保护、返防、唯一炮手、冷却、药品、两个回合起点、重复请求深拷贝、并发、任务 stdout 以及八种真实初始地图资金组合。

已有测试调整并非删除业务断言：依赖 DAG 增加两个新模块；源码冻结比较只增加新策略选择分支的明确例外，并新增入口 AST 断言；HTTP 任务 fixture 增加存活基地，建炮 fixture 使用新炮位的合法相邻格，业务与重复投递断言保留。真正基于子进程的完整响应冻结测试仍因 Flask 缺失而未获通过，不能用 AST 比较代替它。

完整测试命令已经尝试，`full_suite_attempt.log` 记录 Flask 导入失败导致的失败/错误。当前实际执行环境是 **Python 3.13.5**；额外执行了 Python 3.11 语法解析检查，但不是在 3.11 解释器上运行。README 原来记载的上一轮 Windows/WSL 全套通过是历史结果，不能当成本次新代码的验收结果。

### 6.3 1300 步长周期经济连续性

两个起点分别从 0 和 1 开始，每个执行 1300 步、每日外生给 160 金币。最终两组均为三炮三级、基地三级、18 面墙，无模拟器非法动作。逐日资产、买券次数、金币与计时保存在 `stress.json`。

**这个测试没有机器人伤害，没有任务评分；它验证跨天、资源重生、持续消费和升级链路，不是“存活 1300 回合”的证明。** 两组 2600 步与首日矩阵合计 5960 个经济模型状态转移；既有合成观察回放、单元测试不混入这个数字。

### 6.4 密集夜战输入与并发

50/150/350/700 个机器人分别搭配三个种子，共 12 个单步决策场景，验证最终合法性校验、角色控制互斥和重复请求一致性。实际炮数随冷却、目标和角色避险决策变化，不能笼统写每场都射三炮。另把现有 HTTP 测试中的 1302 机器人 fixture 直接送入真实 GameSession 做无 HTTP 的四请求并发检查，响应一致且有三条攻击指令。

这是密集输入下的决策压力测试，不是机器人运动/伤害模拟。具体耗时仅代表本容器本轮测量，不保证比赛机器硬实时上界，也不把与其他测试并行运行的时间差说成可靠性能倍数。

## 7. 仍然存在的风险

最重要的未知是**真实夜战与任务正确率**。新布局和日程改善白天资源效率，但实际机器人路径、墙体阻挡价值、弹道细节、药品时机仍需用平台反馈检验；没有把已经存在的攻击模型完全重写，避免引入无依据的引擎行为。

固定 18 墙并保留两门是候选设计。紧凑炮位可能改变爆炸暴露与拦截关系，静态返程预测在敌人/队友动态封路时仍可失真，3 次卡住重规划也不是通用死锁证明。生成地图中仍有不足 8 墙场景，下一轮应继续检查具体路径成本，而不是盲目把目标数调大。

任务的一次检查包可能截断很长文档、忽略题目未明确引用的依赖，模型仍可能输出错误字段或错误代码。没有伪造“模型准确率已提升”的数据。新闻/寻宝链路仍未纳入新生存策略的主路径。

本次没有实际启动 Flask HTTP 服务，没有在赛事 Python 3.11 环境执行全套，没有官方对战成绩。以上三项均应列为交付边界而非隐性通过。
