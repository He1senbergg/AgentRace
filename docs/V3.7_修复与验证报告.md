# AgentRace V3.7：Round13修复与验证报告

## 1. 版本与交付边界

本次基于用户 `AgentRace(3).zip` 中的 V3.6 修改，覆盖 Round13 game79～90 的故障。交付是可运行的完整单文件参赛候选，不是仅有建议的审计包。源文件 SHA256：`76e7007720de4540b72a8d79897e2006cbeb772181fccefd7390d9fee84714ea`。

参赛包唯一成员：`CoreGeek/main3.py`。标准库 HTTP 服务、平台位置参数端口、print-only 诊断维持原协议；不要求 Flask、agentrace 目录、环境变量或平台日志文件访问。

**没有新官方实机成绩，不能宣称已通过第五/第六夜，更不能宣称1300回合生存。** 所有“回合提前”“维修回血”等下述结果标明属于真实输入探针还是独立的局部状态模型。

## 2. 实现的修复

### 2.1 正确用药与受击记忆

- `medicine()` 在任何使用分支前要求当前血量低于最大血量；满血绝不消耗药品。
- 分开记录相邻连续回合的真实掉血、累计个人受损，以及邻近机器人的潜在威胁。潜在威胁不是实际必受伤害。
- 低于65%血量、实际持续受击或贴身风险下，按条件使用已有药品；没有药、没有钱、背包满时不生成非法命令。
- 一般角色保留1份药；形成主炮且进入中期后，前线或曾经受击的角色允许2份。有预算及完整往返窗口才采购。
- 库存按携带者计算，不假设能够在角色之间转移物品。使用会占用当回合该角色的行动，不再同时指定它操作火炮。

### 2.2 真正的撤离，而非在炮台旁挪一格

- `evade_controller()` 不再先把“不邻接任何炮”的格子过滤掉。
- 对持续受击、无药或危险状态，检查不超过3步的短路线，允许离开炮位。
- 路线遵守地图实际占位和共享目的格限制，沿途潜在压力不增加且终点更低；这不保证敌方下一步不会追击。
- 短期撤退状态使普通回防不立即把角色拉回原受击位置；状态过期、角色死亡、回合不连续或清场时清理。
- 可能因此暂时减少一座炮的操作，这是为保存后续回合的操作员而接受的代价，不宣称零代价撤离。

### 2.3 解除跨天维护断供，但保留当日预算与火力约束

- 删除“三炮没全三级，墙维护跨天累计40金币后永久停止”的实际限制；不靠提高单日数字掩盖旧锁。
- 保留每日真实采购及本回合预留预算：第1天0、第2天20、第3天40、第4天以后60金币；不足既定火力条件时进一步限制。
- 主炮和第二座主炮的核心升级保留优先；保护已有三级炮的关键墙可以先于第三座炮的后续升级。
- 最高优先级目标（包括危急基地券）买不起时，不再阻止所有负担得起的关键维护候选。
- 维护只针对实际可达且来得及送回的目标；对缺炮保留建造费，不使用预期卖矿收入授权同回合购买。
- `stock_repair_kits()` 支持先驱者/顺路角色携带可用补给：单携带者最多2个修墙包，全队最多3个，包含本回合已下单数量。形成关键主炮前不会无限购买维修库存。
- 根据实际破口、累计受损和当前残血排序前墙；同一位置换成新墙ID后不会忘记曾经被突破。避免对计划升级的同一堵墙先用修墙包。

这组变化不保证第三门三级炮在任何场景都与V3.6一样早。明确取舍是：允许有限维护保住已形成的昂贵火力，避免升级目标尚未完成时，原有炮和操作员先被打掉。

### 2.4 短程移动维修与冷却协调

- 增加“移动到墙旁—使用—回到可操作位置”的短维修安排，而不是只支持原地修墙。
- 路径最多3步，检查持有人、血量、实际背包、目标是否还存在、近期承伤和预计可抵达时间；任务有截止时间，不会永久占用角色。
- 普通维修要求预测不损失开火机会；保护关键高价值资产、即将破口时，允许最多1次预计齐射机会让位，拒绝更大牺牲。
- 统计往返与使用的行动占用，而不仅仅看当前炮是否冷却；执行过程中逐回合重算。
- 能够由当前火炮直接清掉整波敌人时，不为不必要的维修阻止清场。
- 人物急救/撤退优先于冒险维修。没有物品、来不及、路线不合法、墙已消失或持有人死亡时取消，不虚构已维修成功。

这里的“最多一次”是当前观测与冷却预测下的计划上限；敌人动作、队友临时占位等可能改变后续可达性，不能当成实机绝对保证。

### 2.5 缺炮时进入战损恢复

- 只在曾经形成完整三炮、现在缺炮且真实白天时启用，开局建炮和清场后的夜间不违反建造规则。
- 现金不够25金币但背包现有矿产能够补足时，优先让最快兑现的工人小批量卖矿，而不是等到10件或背包满。
- 另一个可用工人可以提前到合法炮位准备施工；现金在后续真实观察到账后才建造。
- 有现金但已错过往返/施工窗口时仍然回防，不删除时间限制、不瞬移、不授权夜间建炮。
- 重建首要目标是25金币恢复一级火炮，不要求先攒完升三级的全部成本；之后由正常升级链继续提升。

### 2.6 基地券购买与使用分离

- 已持有的二级升三级基地券，在二级基地血量高于70%时可以留存，不立即浪费其回满血价值。
- 达到受损条件后，仍需要实际持有人到位，并通过原动作校验才能使用；基地危急优先。
- 未承诺自动在所有地图上提前备齐三级基地券，购买仍受现实资金和其他高优先级支出影响。

## 3. 有意保持不变的部分

任务执行器、Prompt构造、分页与部署修复、任务证据校验、伤害和选靶计算、动作合法性校验、GameMemory/HTTP会话协议、14格C形布局与原炮位、清场后的夜间出工机制保持不变。

对15个任务/战斗/协议核心定义进行AST比较，与V3.6完全一致，名称见 `验证结果.json`。生产文件由3980行变为4202行，新增222行；测试夹具、旧基线和局部模型仅用于本地验证，不在平台单文件导入路径中。

## 5. 连续执行验证：动作确实改变了模型状态

### 5.1 game89战损恢复，真实起点＋独立经济模型

起点为实际第521回合；新旧版本分别连续运行50个回合，每回合真正应用自己的移动、卖矿、建造、库存和金币变化。不加入机器人AI/伤害、不新增任务奖励；矿点搬迁采用固定种子的合成规则。

- V3.6：第563回合才卖出10块铜，到第570回合仍未重建。
- V3.7：第535回合卖出4块铜，第536回合重建一级火箭炮。
- 两版模型动作校验均无拒绝；没有用未来现金购买、同回合卖矿后直接透支建造。

**535/536是该局部模型产生的结果，不是V3.7已在官方平台执行的回合。** 该模型不能评估重建后能否扛住夜战。

### 5.2 短夜战维修压力

设置一堵500HP残墙、距维修格一步的携带者、一份修墙包和冷却中的炮；对墙外部施加每回合80点固定伤害，敌方位置与选靶固定。两版执行12回合。

| 指标 | V3.6 | V3.7 |
|---|---:|---:|
| 实际在模型中使用修墙包 | 0 | 1 |
| 修墙时HP恢复量 | 0 | 1080 |
| 12回合结束墙HP | 0 | 620 |
| 火炮齐射命令数 | 9 | 9 |

新版先移动，随后消耗背包修墙包，把当时420HP的二级墙恢复至1500HP。模型再继续扣除外部伤害。该测试证明移动维修、库存扣减和冷却安排能协同执行；**固定80伤害压力不是官方机器人AI，也不证明实战不会少开炮。**

### 5.3 其他连续场景

携带两份药时，满血不喝，注入两次真实HP下降后才分别消耗；基地券先购买、走到基地旁，健康时保留，注入受损后升级并恢复；目标墙被摧毁或维修者死亡，及时清理过期维修任务。这些连贯场景共7项，均通过。

原V3.6的105项现行测试在修改前全部通过。最终保留95项，其中10项旧策略断言已经与这次修复相矛盾（例如绝不移动维修、即将破口仍绝不能让出射击、跨天40金币、库存必须恰好一瓶/两包等），予以明确退役并用新正反例替代，不把这些测试算成原样通过。结果JSON列出全部16条历史退役规则，其中6条由V3.6阶段继承、10条为本次变更。

## 7. 平台操作

1. 保留V3.6回滚文件，直接用本次 `CoreGeek.tar.gz` 走原来已成功的上传流程；只需其中的 `CoreGeek/main3.py`。不用额外模块，不改平台注入端口，不设环境变量。
2. 本地仓库需要同步时，将覆盖补丁解压到现有仓库根目录，覆盖同名文件。不要在原仓库内再套一层目录；不删除日志和现有环境。源码、CoreGeek入口和包内入口相同。
3. 平台启动打印应为 `build=v3.7-sustainment-recovery` 和 `survival policy=v3.7-repair-retreat-rebuild`。`deployment_crlf_v34`、`heritage_cursor_v34`仍保留，不代表运行错版本。
4. 使用固定版本跑红蓝交换，保留胜负、分数及原始print日志，不删除REPLAY3行。无需进入平台目录或下载任何自建文件。先检查满血耗药是否消失、夜间实际维修是否发生、关键前炮存活时间、缺炮到重建时延，再按官方基地先毁判负规则判断胜负。
