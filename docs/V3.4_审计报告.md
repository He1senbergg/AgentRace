## 2. 首要根因：上一版API技能实现了错误的分页协议

game43第19回合，对应 `log/Versus/round10/game43/ally_BlueSide_667.log` 第152行起的完整回放，执行结果为：

```text
[exitCode:1]
[run_heritage] NeedReasoning: Pagination repeated a page. Metadata: {"total_count": 15, "offset": 0, "limit": 10}
```

同局第148回合、原日志第1028行起再次出现南京的 `total_count=12, offset=0, limit=10`。其余11局有同类明确失败，逐任务回合与原始行号见 `证据与验证.json`。

实际服务按offset/limit分页。旧代码却循环page=1、2……，服务忽略page，重复返回第一页。北京15条、南京12条，都超过单页10条；成都只有10条，刚好不需要翻页，所以看起来“有时成功”。这是确定性的实现错误，不是模型随机发挥，也不是已经修好的部署CRLF问题又复发。

此前为V3.3建立的本地API测试使用了page/total_pages契约，没有覆盖实际offset/limit；因此测试没有检出本轮故障。这是先前验证方法的缺陷。

### V3.4已实施

执行器读取当前响应中的分页元数据。遇到offset模式，下一页使用“返回offset＋实际收到的记录数”，清除page参数；不会按请求的100条页大小盲目加100。保留真正page模式的兼容，不把两类混在一起。校验总量稳定、游标一致、重复/重叠记录、提前空页；401、500、未知年代等均非零退出，不能把错误包装成“0条遗产”。

认证、城市、端点、字段仍来自本次任务文档和实际响应；没有内置城市答案或历史令牌。stdout只保留可提交的当前答案，诊断写stderr，平台仍会把命令结果带回print回放。

部署快捷技能保留现有CRLF处理，检查器文件不修改。新技能标识分别为 `deployment_crlf_v34`、`heritage_cursor_v34`。

## 3. 第二个任务问题：会做题，不代表接任务和调度正确

任务规则见 `Official/任务书.md:252–254,357–364`：各队两个任务点，任务总数有限；任务结束后等待30回合，失败也会消耗该项任务。旧调度把“当前没有可立即接取的任务”过快转成物流工作，开拓者经常离开任务区；冷却结束后仍在运输升级券。

日志还显示，冷却期间的任务字段可以是 `isValid=false, timeoutRounds=0, scoreReward=0`。这并不等于任务永久耗尽。相反，冷却归零仍无效才不能继续等。两任务点在数组中的排列顺序也不是固定任务编号。

V3.4会在当前对局中、确认一次合法快捷提交结束且无错误后，记录对应任务点的实际耗时。以后根据走路、冷却、解题和回防剩余时间决定等待/接下一题；未验证任务仍使用保守超时预算。已耗尽点不空等；数组重排不改变任务点身份。能完成的任务优先于尚未购入的普通采购；已买券的背包和投递目标不会丢失。

没有写死“总能3回合解题”或“每天无限刷新”。能力学习仅在本场生效，不缓存其他对局的答案。

## 4. 你的C形墙方向得到日志支持，但不是“背面绝对安全”

对本轮每个夜晚起始观察，累计2,709个指向我方的机器人均出现在面向地图中央的一侧。这里统计的是本轮已观察到的机器人，不是规则对所有未来刷新的保证。任务书没有提供“永远只有单侧”的硬承诺。

同ID、同等级围墙在相邻回合间可直接核对的掉血累计149,585；背面一列仅155，占0.104%。这个口径不包含围墙从日志消失那一刻无法直接读出的最后一段伤害，也不会把升级恢复血量计算成负伤害。背面不是零受击，但资源价值明显低于正面。

### V3.4已实施

最终目标从旧版18堵，调整为14堵的前向C形：正面6格先建，上下侧翼各延伸4格，背面留开口；左右出生点镜像。完整围墙圈是20格，C14相对完整圈少6格，但**相对旧代码18格目标实际少4格**。不能把少墙数量报错。

不是只删除几堵墙。炮位也重新排列，让两个炮位接近开放背面，一个炮位靠前侧；14堵墙全部建成后，每座炮仍至少有两个静态可操作空位，后方保留出入路线。第一稿C形封闭旧门洞后，连续联调发现过操作员挡住带券同伴的问题，当前交付已修正该候选布局；不把这一候选期发现冒充旧版实机故障。

少建墙只省石头与工人回合，**不会凭空增加升级金币**。前线升级依然需要任务和采矿收入。

### 从“墙数量指标”改为“前线受击维护”

旧版这12局没有使用过围墙升级券或WallFixer。新策略按实际掉血、剩余血量和朝向给前线墙排序，不再等待三炮三级、基地三级才允许升级墙。高压前墙可插队升级到二级/三级；无受击背墙不吃预算。

规则确认墙升级恢复满血（`任务书.md:260–277`），所以升级既增加上限，也能在受损时恢复血量。另增加少量修墙包储备，并在严重受击时由邻近或短途可达且有库存的角色维护。路线太长、预计来不及、角色风险过高或没有物品，就不伪造修理动作。

为避免维修吞噬所有武器资金，维护支出设每日上限，修墙包预备库存上限2；这些是候选策略参数，不是比赛规则。C形仍可能被侧翼/绕后机器人突破，后续必须检查真实受击位置。

### V3.4已实施

1. 本轮默认改为三座火箭炮，优先完成第一座三级，再推进第二座三级；不再长期保留无人投资的一级电磁炮。
2. 基地一级到二级保留较高优先级；严重掉血时基地升级可抢占普通投资。基地安全时不机械优先花150升三级而拖延第二座主炮。因此白天无伤害模型里候选基地会保持二级，这不是声称三级基地无价值。
3. 在实际金币、库存和回防时间允许时，一趟携带多件升级/维修物品；同一目标可连续处理一级券和二级券。每件物品独立记录目标，新的采购不能覆盖前一张券的去处。
4. 空闲开拓者可提前到商店等待工人卖矿带来的现款。只是提前走路，购买仍检查当回合真实金币，不透支未来收入。
5. 带武器券的角色优先回到该目标炮台的操作位，避免买了券却回到另一座炮旁，整个夜晚用不出去。

### 为什么没有又把全部战斗代码推倒

保留已有伤害计算、重叠导弹伤害和威胁/击杀选靶权重。火箭每枚中心20、邻格10、升级增加导弹数，冷却3回合，见 `任务书.md:230–236`；三级射程40来自任务书武器属性表及实际状态字段。

三火箭是针对群体入侵和尽早远距离削血的策略选择，**不是所有状态都支配电磁炮**。例如少量孤立目标场景，电磁炮的连续射击可能更有价值。当前修复的确定性部分是任务分页、调度和采购落地；三火箭与C14属于必须实机验证的战略取舍。没有实现专门抢对手机器人积分的路线，也没有在这次加宝藏支线。

## 8. 尚未证明的事项

API记录为合成、独立构造，不能代表未来所有任务类型；新类型或未知协议仍回退模型。C14主要依据本轮入侵方向，未来偏转/绕后风险存在。三火箭和前线维修会改变夜间行动分配，可能牺牲部分单体持续火力或某回合射击。日志与规则并未提供完整官方机器人AI，本次没有伪造十天闭环生存。

改动目标是“少丢任务收入、把券及时用掉、把墙和火力集中到真正受击方向”。是否由第五夜进一步推进到第十夜，需要真实比赛确认；不能用离线测试数量代替这个结果。
