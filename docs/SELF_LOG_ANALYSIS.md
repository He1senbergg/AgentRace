# Self/1.log 实测分析与修正

## 证据

本文件分析用户提供的 `log/Self/1.log`，共93条HTTP记录、15条回合摘要，观测摘要覆盖1–10、25、44、50、69、87回合。它不是完整请求回放，不能据此计算整局动作成功率。

|---|---:|---|

## 确定的问题

1. **昼夜从未识别，防御策略被停用。** 旧实现仅观察到0才能自动识别；真实开局roundNo=1。construct/fire/position_controllers均依赖phase，因此现有自动启动方式无法建造、开火或回防。依据AI Spec §3.2的“首场以实际首回合确认”及demo一致的开局证据，现已支持首观测0/1自动识别。显式配置优先，中途从5等回合接入仍不猜测。
2. **任务/宝藏优先级可能抢占炮手。** 代码原先先分配这些动作再开火/回防；回归用例已复现先锋在夜间接新任务使邻接武器不开火。改为先防御再分配新任务/宝藏，活动任务主人仍不得违规移动或被强行征用。

## 仍需真实观测的问题

- 工人采同一矿不等于错误：§20允许共同采集，矿采10次后消失并换位置。当前日志缺每回合地图与背包，不能断言8回合离开是寻路震荡；不据此盲目修改采矿规则。
- 多次任务超时已经确认，尚不能判断是LLM无返回、返回格式不匹配、探索过多还是题目难度。新摘要记录返回类型/长度/决策JSON是否有效、任务pending/deadline/expired，不记录任务原文或答案。
- 防御布局、经济往返收益、真实开火效果尚未平台复测；修复启用条件不等于策略已达到高胜率。

## 新增观察能力

[trace_turn]：前10次、之后每10次、昼夜边界和限量异常；增加矿物库存、背包总数、武器/机器人数、任务状态。
[trace_map]：首观测、每50次、日内1/70/71/130边界输出当前41×32地图，x向右、y向上；显示完整基地占地、矿物、商店、任务点、双方单位和机器人。它是当前观测图，不能补回旧日志缺失地图。每类角色/动作摘要最多12项，地图展示全部有效坐标对象。

## 验证

完整100项测试通过（9.032秒），包括真实HTTP、密集/并发请求、2600回合观测回放。新增4项回归验证1基实际初始坐标开局建造→首夜攻击、显式0基与中途接入、夜间炮手与新任务竞争、地图方向/基地占地/文本不泄漏。开局回放仅模拟移动和建造，不是官方战斗模拟，不证明伤害结算或胜率。代码复核检查了phase边界、锁内缓存与诊断异常隔离、活动任务限制及地图占地；没有修改协议或动作校验。

# Self/2.log 最新运行分析

## 日志与动作的区别

文件336行，105条POST访问日志、22条回合摘要（1–10、20、26、30、40、45、50、60、70、71、80、90、100）。全部22条摘要都有至少1个动作。没有摘要的83条HTTP访问不能据此判定为空动作，也无法从日志确认每条对应的roundNo。HTTP 200只表示HTTP响应成功。旧诊断前10回合后每10次采样，是大部分回合只显示200的直接原因。

第1–3回合建造，第4回合金币0且三座武器实际存在，说明上次昼夜/建造修正已生效。第80/90/100回合存在attack；第80回合feedback包含火箭20040上一回合成功，不能因采样看不到火箭attack就判定它未开火。武器动作以武器ID为键、controllerId指定操作角色，炮手不另发move。火箭有3回合冷却（AI Spec §17.4），旧摘要未记录cooldown，不能确认某次未开火的具体原因。

## 本次改动与范围

增加每个已提交非缓存回合[turn]摘要：动作/反馈、角色control_weapon/active_task/no_command等状态、武器等级/冷却/射程/邻接角色、任务pending与LLM/沙盒输出长度。no_command仅表示本回合未给角色动作，不伪造唯一原因。详细地图仍采样，敏感任务和命令原文仍不输出。已有日志不可补回漏采样回合。

本次没有改采矿评分、领取任务或武器选择策略；上述瓶颈是代码和日志对照分析，不把诊断改动当作胜率修复。后续策略改进优先级：任务领取预留回防时间；采矿纳入出售往返成本和提前变现；采购/升级预留日间路程，再评估炮手位置与武器分配。分别需要动态资源与路径回归，不能仅靠本次静态摘要验证收益。


# Self/3.log 逐回合分析（2026-09-10）

## 核验范围

仅分析本地 `log/Self/3.log`、当前代码和 AI Spec；未访问 Official 或外部服务。本次不修改策略代码。JSON统计：97条HTTP、97条[turn]（R1–97连续且唯一）、22条详细摘要。191条动作：move 129、collect 21、build 3、acceptTask 3、attack 35；sell/buy/use/submitAnswer均为0。190条已记录动作反馈均true，最后R97动作没有后续反馈。按补充规格，true仅表示动作合法，不等于伤害或任务成功。

## 主要发现

1. **真正整回合空动作仅R77、78。** 两回合火箭cooldown分别3、2，炮手已邻接；其他武器射程为3/6。结合fire逻辑，短射程武器当时未选出正收益目标，但日志未逐回合记录机器人坐标，不能确定是无射程内目标还是弹道/评分筛选。R68–75工人未下令主要对应回防驻守，先锋仍移动。no_command本身不包含调度原因。
2. **经济全程未变现。** R4–97金币始终0。10010移动55次、采矿9次；10012移动54次、采矿12次。R43起背包分别6铜+3铁、5铜+7铁，R90仍原样携带，按已记录价格合计价值85金币。workers只在库存达20或已邻接商人时主动卖矿；选矿price/(len(route)+5)未考虑卖矿和返防成本。回防先于经济执行，导致不足20矿也直接带回炮位。采集总量仅21，不能把109次工人移动视为有效经济收益；但反馈/坐标支持移动确实发生，不能称为卡住不走。矿采10次刷新解释部分长途换矿，无法用采样地图重建每次选矿。
3. **三次任务均未交答案而超时。** R8/27/57领取；deadline为23/42/67；R24/43/68错误码1。三个窗口分别发出8/8/5次prompt，7/7/5次executeCmd，共19条命令，submitAnswer为0。LLM决策确实被解析并驱动沙盒命令。TaskPlanner仅以prompt提醒临近期限提交，没有强制收敛阶段；前两次最后可用回合仍发prompt，下一回合已超时。缺少lastCmdResult的exitCode、TIMEOUT、截断等摘要，不能声称19条命令执行成功，也不能断言具体解题失败原因。
4. **先锋R43–54连续12回合无任务也无动作。** task_options仅选isValid=true且coldDownRounds=0的任务，无可选任务时TaskPlanner直接返回，先锋也不在workers采矿范围内。规格§31.3规定任务结束后30回合刷新，与空档相符；但摘要未记录playerTasks，不能确定每回合具体冷却/可达性。R55恢复移动，R57又接任务，R68才返防，R76才邻接火箭。说明空档没有用于提前准备，而且接任务仍未预留时限加返程。
5. **火箭确实发射，随后因炮手减员停火。** R76/80/84/88发射，随后反馈均true；cooldown按3→2→1→0变化，符合§17.4。R91先锋不再出现在activity，火箭邻接列表为空；R92–97冷却0仍不开火。fire先遍历非火箭、占用工人，position_controllers随后只看未占用角色：R91–94两个工人持续操作机枪/电磁炮；R95–97仅10010操作机枪，邻接电磁炮却无法再操控，火箭也无补位。固定顺序没有比较转移炮手后的收益，不能保证剩余火力最优；尚不能凭摘要计算换炮的精确收益。
6. **始终一级防线，伤亡后缺乏调整。** 所有武器观测level=1；全程无采购/升级/治疗/维修动作。R80基地1500血，R90只剩810血，先锋15血、工人10012为80血；R91先锋消失，R95工人10012消失，三座武器仍在。末条仅R97短摘要，没有最终基地HP或胜负，不能报告比赛最终结果。
