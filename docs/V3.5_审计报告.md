# AgentRace V3.5：Round11审计、修改与验证

## 1. 本次材料与结论边界

本次只以新上传 `AgentRace-main(6).zip` 内的 `Official/任务书.md`、`Official/接口文档.md`、实际 `src/main3.py` 和 `log/round11/game55～66/ally_*.log` 为依据。12局启动与REPLAY3版本均为V3.4；没有用对话里自动展开的V3.2.2旧日志充当最新实机数据。

## 2. 任务：本轮不再归咎于Prompt

72次任务均在3个活动回合内结束；72次最后submitAnswer在下一回合反馈True，未见任务错误，结束回合都有任务积分增加。48次加97分、24次加105分（依本任务实际奖励/时间规则，不把两者差异解释为失败）。每局均完成6次，部署36次、API36次。

API offset分页、认证、字段统计及部署CRLF处理保留。当前执行器、内层答案校验与CombatPlanner做AST/文本比较均未改变，详情见unchanged_components。任务接取与路径预算会使用新的安全工作窗口，但不会复用历史答案或写死某城市结果。

旧版把第5、6项任务推到第二天做，意味着同样的任务金币来得更晚。清场后的夜间也允许接任务，因此此处仍有调度收益，而不是需要继续修改正确的解题器。

## 3. 清场后的夜间工作：确定的大量空转

### 3.1 规则依据

`Official/任务书.md:91～96`：白天70、夜晚60回合，机器人全图可见。
`Official/任务书.md:138`：建造仅限工人且白天可用。
`Official/任务书.md:118～173`：移动、使用物品、交易、采矿等各有角色/距离条件，没有统一夜禁。
`Official/任务书.md:462～466`：机器人在夜晚第一个回合统一出现，次日早晨残余清除；召唤令叠加在下一夜浪潮。

因此不能把“时间是晚上”直接等同于“整队只能站在炮边”。也不能把安全工作状态伪装成白天，否则会错误放开夜间建造。

### 3.2 日志结果

12局在基地尚存、夜间本方目标机器人已经全部清除的窗口共867回合，其中**866回合整张roleCommandMap为空**，另外1回合仅有移动。没有采矿/买卖动作。仅前两夜就有856回合这样的窗口，平均每局71.33回合；累计相当于又一个70回合白天没有用于工作。

例如game55在96～130及226～260清场；每晚剩35回合，却一直等次日才继续。game64还在第三夜380～390出现11回合空窗。

### 3.3 已实现

新增economy_window与NIGHT_WORK，逐回合读取真实全图机器人状态。夜晚首回合不放行；本方目标或未知归属机器人尚存、机器人字段异常时都继续防守。清空之后允许移动、采矿、卖矿、采购、投递/使用升级券和可完成的任务。

对方仍存机器人不直接阻止所有工作，但规划避开其周围4格；对方机器人逼近基地6格内则不放行。遇到新增本方威胁立即撤销安全工作状态。没有把日志里的96、226等清场时刻写入生产策略。

工作预算同时计算本夜剩余时间与下一白天，仍保留回炮位的路径和安全余量；最终窗口不超过1300回合。真实Phase保持NIGHT，ActionValidator的夜间建造禁令未改。

## 4. 投资：高等级主炮并不等于完整火力

### 4.1 实际花钱和升级

全12局每局最多都只有**一座三级火箭炮**；其中11局另外两座没有升过二级。game64曾有第二座二级炮，但也没有第二座三级炮。后期部分一级炮被打掉，不能只看失守时还剩几座炮。

12局已确认采购支出：

| 项目 | 金币合计 | 说明 |
|---|---:|---|
| WeaponUpgradeVoucher1/2 | 3100 | 13张一级券、12张二级券，几乎只完成每局一个主炮链 |
| WallFixer | 850 | 85个维修包 |
| WallUpgradeVoucher1/2 | 1030 | 墙升级；加维修共1880，均值156.67/局 |
| Medicine | 760 | 76份药品 |
| StationUpgradeVoucher1 | 700 | 7次基地二级；没有基地三级券采购 |

不是说墙修复没有价值，而是其目标覆盖、优先级与运输安排会持续压住长期投资。例如game59的墙维护就花250金币，等于把另一座一级炮升到三级所需的100+150金币；这只是机会成本比较，不是保证搬走这250就一定来得及完成升级。

### 4.2 确定的代码冲突与实证

V3.4给备货WallFixer优先级17，高于基地一级升级20、副炮升级22/24等。库存备货还能触发专程往返商店。game55第200回合有190金币，炮级为3/1/1、基地一级1470HP，记录的资本目标仍是10金币修墙包（日志1250～1251行的回放，紧邻shadow可核对）。game56第330回合191金币，仍3/1/1和一级1495HP，最新记录的资本目标同样是修墙包。shadow目标是最近的采购意图而非本回合成交；这里结合实际源码优先级说明问题，不把这个字段当成真实消费。

game56第294回合修复(12,21)的墙，第297回合又给同一墙升级。规则升级即回满血，期间为白天，没有必要先耗一个维修包。对应回放打印行1810～1811、1822～1823。

工人的墙材料quota也有跨日/新一趟遗留：收工前被压成1石头，下一趟继续1块一运。只调整金币比例不能修复这类工时浪费。

### 4.3 已实现的采购安排

常规永久投资顺序为主炮1→2→3，基地至少二级，第二炮1→2→3，第三炮1→2→3，随后三级基地与墙维护；基地血量低于45%时救急目标可前置。已购到的基地券在实际夜战危急时仍优先使用。不是不顾人物/基地生死的机械炮优先。

墙的采购目标和库存缺口分别计算；已有升级券只覆盖一个具体目标，不可同一张券覆盖两个炮。多角色在同一回合分配运输时共用金币预留账，其他采购和健康人员备药不得花掉在途升级的预算。连买二级武器券也遵守该预留。

已有物品的配送不被普通采矿任务擦掉；有可用升级券时不先给同墙使用维修包。工人开始新批次/新天时重估石头批量，不沿用昨日的1块配额。健康角色只机会性留1份药品，不再2份一补。

### 4.4 围墙等级范围与每日额度

这是本版可调的实验上限，不是官方规定，也不是“这些墙一定扛得住”的证明。不强制把预算花满；只对实际受损、承压的墙升级。

| 天数 | 正面6格等级上限 | 侧翼上限 | 墙升级+维修采购金币上限/天 |
|---|---|---|---:|
| 第1天 | 1 | 1 | 0 |
| 第2天 | 1 | 1 | 20 |
| 第3～4天 | 至少两座三级炮后允许2；否则1 | 1 | 40 |
| 第5天 | 至少两座三级炮后允许2；否则1 | 三座炮全三级后允许2；否则1 | 60 |
| 第6～10天 | 三座炮全三级后允许3；两座时最多2；不足两座时1 | 三座炮全三级后最多2；否则1 | 60 |

武器目标仍排在非紧急墙升级前，表中“允许”不等于当天一定购买。维修库存不足一份时才补，三炮都三级后最多两份；完整墙的备用维修包只能顺路买，不专门跑一趟。已购维修物品仍可夜间救急，采购上限不禁止使用已持有物品。保持V3.4的14格C形墙，不拆掉现有边翼，也不增加绕到对方的抢分路线。

### 4.5 火力的量级

依任务书364行，火箭每枚中心20、周围10，升级增加弹数，射后3回合冷却。完整三炮从3/1/1到3/3/3，在全员就位且目标可打的条件下，每4回合的导弹由5枚变9枚，理论弹数增加80%；另外两座炮也得到三级40格射程。该数字不是实测击杀速度，弹着重叠、机器人密度、冷却和炮手动作都会影响实际伤害。

22项真实本机TCP/HTTP测试通过：目录中只有提交用main3.py，python -S -B且清理环境变量；测试位置端口、POST、重复请求、错误输入、分块传输、print回放完整性。目录没有生成额外文件。实际测试Python3.13.5；Python3.11语法与标准库检查通过，但官方Python3.11.10容器没有实测。

### 5.2 真实请求兼容性重放

9,560个最新历史请求按各局顺序输入新版，异常0；实际任务活动回合中Prompt、executeCmd、提交答案链输出变化0。867个清场观察被识别为可工作的夜间窗口。

后续请求仍来自旧策略实际世界，不是按新动作生成，因此它只证明接口和状态处理兼容，绝不从中计算新版得分。
