# AgentRace 当前 Prompt 与 LLM 任务链路审计

审查日期：2026-09-12。输入：用户本次上传的 `AgentRace-main.zip`。本报告审查的是附件快照，不是未能访问的远程分支，也没有把历史文档当成当前源码。

## 1. 结论

当前赛事 LLM 主要负责开拓者的自进化任务：读懂题目与任务资料，提出沙盒命令，利用返回结果作答。它不是默认防御模式下负责建墙、买炮、安排工人的全局决策模型。

当前 prompt 有基本工程约束，不是一个空泛的“你是智能体”。但是，当前默认生产路径仍然存在可离线复现的收尾与格式修复缺口；上下文存在重复与非语义截断；SOP 复用仍是近期未验证经验的直接拼接。不能因为协议测试通过或版本号已到 V2.4，就认定模型任务能力已经验收。

本次已有实际证据：读取当前源码及调用链；统计 Round6 七局 4,245 条唯一 [turn] 记录；在当前默认 defense 模式下运行 10 项专门的离线行为检查。原有仓库中的 142 个文件与 ZIP 字节逐一比对，没有改动。

“10 项检查通过”的含义是成功复现所列现有行为，不是这些问题已经修复，更不是比赛模型答题通过。

## 2. 比赛为什么需要 LLM

官方任务书区分三个方向：世界新闻中的推理类任务、民间传闻中的长上下文寻宝，以及任务点领取的自进化任务。新闻影响采矿与交易；寻宝要求推断时间、地点、物品并实际行动；自进化任务要求和沙盒交互，最后提交答案。

官方天气接口案例是：先读接口文档查询北京，再把探索得到的方法用于查询上海、广州。这里“自进化”的具体要求是形成可复用 SOP/SKILL，并非程序在比赛中训练模型。该例来自任务书，不是从这批比赛日志恢复出的实际题目。

当前默认 `defense`：`StrategicPlanner.run` 调用 `TaskPlanner`，不调用 `NewsPlanner` / `TreasurePlanner`。`legacy` 路径保留新闻、寻宝实现；不能把 legacy 测试当作默认模式已经具备的能力。

核心流程为：

```text
开拓者接任务
→ phaseTask 带回任务正文
→ 题目提到 .md 时，程序先自动探索任务文档
→ 组织 prompt，请模型给出 command 或 answer
→ 下一回合读取 llmResp
→ command：交给 executeCmd；下一回合获取 lastCmdResult，再请求模型
→ answer：把字符串交给 submitAnswer
→ 观察后续任务状态和判题反馈
```

程序自己的答题指令、模型建议的沙盒命令和最终判题答案是三个不同层次。`lastRoundRoleActionResults=true` 只表示动作合法，不表示答案正确。

每个游戏日为 130 回合，普通阶段最多调用 LLM 3 次；执行自进化任务期间豁免此限额且不占普通配额，但任务回合期限依然存在。沙盒不能访问外部网络，单命令最多 15 秒；返回输出超过 64KB 会标注截断。

证据：`Official/任务书.md:347–437`；`Official/接口文档.md:21–34,130–140,181–210`；`src/agentrace/strategy.py:50–76,1052–1062`。

## 3. 当前实际 prompt

### 3.1 静态规则与动态上下文

实际生成位置：`src/agentrace/task_news.py:140–174`。主体为英文，概括为：只解决当前游戏任务；返回严格 JSON；在 answer 字符串与 command 字符串中二选一，可带 skill；不输出 Markdown；遵守沙盒环境、权限、超时及 URL 编码要求；失败后查看错误；不要编造未知字段；为提交答案留回合；不要重复无证据的错误答案；剩余回合少时强制交答案。

程序还会拼入：

| 字段 | 实际内容 |
|---|---|
| task | 当前完整题目文本 |
| observation | 本次观察或上一命令执行结果 |
| answer_only | 是否已进入仅答案阶段 |
| commands_used / remaining_rounds_estimate | 已用命令数、估计剩余回合 |
| recent_history | 最近 8 次观察，每次按字符截为头尾，目标限长 4,096 |
| previous_answer / previous_command | 上一个答案或命令 |
| current_skill | 模型给出的过程摘要/可复用方法，最多保留前 2,000 字符 |
| task_documents | 自动发现的文档执行结果，目标限长 32,000 |
| experience_unverified | 最近 4 条未验证历史经验，不做相关性检索 |

当前 `TaskPlanner.prompt` 与仓库 `tests/fixtures/v22_baseline.py` 的同名方法 AST 完全相同。这能证明核心 prompt 未相对该冻结基线发生语义改动；不能据此证明每份历史日志的整个部署版本与当前一致。`TaskPlanner.run` 的对应差异是任务结束归档改为调用 `finish_task()`；近期修复没有重做这里的提示词与解析逻辑。

### 3.2 合理的部分

已有任务、角色及上一回合 pending 关联，避免把迟到结果当作当前任务指令；先找文档，避免开局完全盲猜；命令错误、截断标记会进入上下文；严格拒绝重复 JSON 键、NaN、非法 Unicode、同时输出 answer 与 command 等异常；终局禁止继续执行探索命令，避免不可能及时返回的调用。

这些应保留。问题不在于“规则都没写”，而在于若模型没有遵守，后续流程仍过分依赖它自行修复。

## 5. 当前代码中可确认的问题与改进方向

### P0-A：最终阶段缺少独立协议与有证据的答案保底

通用 prompt 开头始终允许 `answer` 或 `command`，在 final 模式下再追加“必须 answer，command 不执行”。这不是清晰分离的单阶段输出契约。程序确实拒绝最后阶段继续探索，但它没有结构化的候选答案池，也不会从 skill 自动生成一份保底提交。

离线检查：在当前默认 defense 模式构造一段真实模块调用序列，命令返回了城市字段，skill 中也保存了该部分答案；模型在最后三轮持续给出格式合法的 command。程序拒绝命令，直到结束没有任何提交。事实说明缺少保底机制，不说明应把任意 skill 文本直接提交。

官方接口明确：任务超时以此前已提交答案中通过率最高的一份结算。因而将“已有工具依据的部分字段”作为独立候选答案保存并在截止前合法提交，有直接规则价值；字段缺失、unknown、null 的表达必须服从具体题目，不能为了保底编造字段。

建议：探索与提交使用不同静态模板；final 模板完全不出现 command 选项。程序维护候选答案、题目输出 schema、字段来源和提交记录；有证据且格式合规的候选提前留出提交回合，必要时再改进。不要把程序认为“有证据”混同于判题器已经确认完全正确。

证据：`task_news.py:143–174,269–289`；`Official/接口文档.md:140`；离线检查 03/04。

### P0-B：解析失败的修复丢失了出错对象

`parse_llm_decision` 失败后，新的 observation 固定为“LLM response missing or not valid decision JSON; return the required JSON.”。上下文没有原始无效回答，也没有“answer 应为字符串却得到 object”“多了 reason 字段”等具体原因。

因此当前程序主动构造的修复请求无法准确告诉模型要修哪一段。官方材料没有保证服务端自动保留会话；不能把可能存在的模型端记忆当作工程保证。

例如下面的前者会被拒绝，后者才满足当前内部协议；它们只是合成格式示例：

```json
{"answer":{"city":"Beijing"}}
```

```json
{"answer":"{\"city\":\"Beijing\"}"}
```

外层 answer 是交给程序的字符串；字符串内部是否还需要 JSON，取决于题目。当前 prompt 正常阶段没有这样清晰的配对示例。

建议：保留严格终态校验；将解析结果改为分类错误，修复请求带受控截断的原回答与具体错误，只要求修格式。可评测安全的完整 JSON 代码围栏去除，但必须重新严格验证，不用 eval，不从任意文本正则抓第一对大括号，不擅自执行从脏输出中抽出的命令。

证据：`task_news.py:62–73,255–258`；`actions.py:274–293`；离线检查 01/02。

### P1-C：上下文既重复，又可能丢关键证据

每次调用前会把当前 observation 写入 history，然后把 observation 和包含它的 history 一起发送。自动文档发现结果还会长期存进 task_documents；读取文档的当轮同一材料因此至少完整出现两份，并在历史中出现头尾片段。

离线样例：一份 12,138 字符的合成文档结果，生成了 34,845 字符的 prompt；起始标记出现 2 次，末尾标记连历史片段出现 3 次。这个数字是合成复现，不是还原某个真实题目的 prompt。

截断也只按字符：命令结果保留头尾至目标 16,384；history 条目目标 4,096；skill 直接前 2,000。一个 18,036 字符的正常命令输出，关键字段放在中间时，会从下一条 prompt 中消失；截断标记仍然存在，故程序没有假称完整，但模型必须重新获取丢失内容。

建议：稳定文档、当前观察、历史事实分区；同一内容只放一份。历史保留“命令目的→结果摘要→关键字段→来源”，不要直接复制大段原文；长结果按题目字段/JSON 路径定向提取。实现总上下文预算，但先核实模型实际窗口与计数方式，不自行宣称某个 token 上限。

证据：`task_news.py:43–58,140–152,261–264,271`；离线检查 07/08。

### P1-D：重复失败操作只是被提示不要做，没有确定性拦截

prompt 要求不要重复失败命令或无新证据的错误答案。但当前 run 只要解析出合法 command/answer 并满足动作门禁，就再次执行或提交。

离线检查已复现：同一命令 exitCode=1 后原样再执行；同一答案被错误码2拒绝后，在没有新工具结果的情况下再次提交。

建议：按任务实例记录操作摘要、参数、执行状态和证据版本。对确定性错误设置去重；瞬态失败保留有限重试，不把所有相同命令永久禁止。重复答案只有在需要重发、前次动作未合法执行等明确定义场景才放行。

证据：`task_news.py:160–166,269–283`；离线检查 05/06。

### P1-E：skill 混合了可复用方法与当前部分答案

prompt 要求在 skill 保存部分答案，又把 skill 定义为可复用 procedure。同一字段同时承担“本题当前事实”和“跨任务方法”，并直接截为前 2,000 字符。

任务结束后，无论具体成败，经验统一标记 `ended; correctness unverified`；下一题注入最近 4 条，不做任务类型/接口版本/参数模式匹配。保留 unverified 标签是审慎的，但它并不构成一个经过验证的技能库。离线检查中，不相关的排序任务经验仍进入城市任务 prompt。

建议：分开 `candidate_answer` 与 `reusable_procedure`；跨任务记录接口、参数、解析规则、环境前提和成功证据。失败经验作为失败模式管理，未验证经验只能当候选，不与成功 SOP 混同。不保存或复用城市温度等一次性答案作为通用方法。

证据：`task_news.py:150–163,270–271`；`memory.py:161–173`；离线检查 09。

### P1-F：程序的最终校验是协议/动作校验，不是题目字段校验

模型 answer 只要是非空字符串，动作位置等合法，便会原样进入 taskAnswer。程序不会依据题目要求核对必填字段、数值类型、单位、额外解释文字等。离线检查中，要求 city 与 numeric temperature 的任务收到一段普通散文，也会发起提交。

这不意味着程序能通用判断任意题目的真值；合理目标是先支持已识别任务类型的 schema 校验与确定性格式化，减少本来可以在本地避免的错误。模型输出的内部控制 JSON 与判题器要求的答案 schema 必须分开。

证据：`task_news.py:62–73,272–276`；离线检查 10。

## 6. prompt 如何改，而不是只把英文翻译成中文

首先修提交保障和解析修复，其次减少上下文冗余，再完善 SOP 检索与任务 schema。语言可以按赛方模型做中文/英文对照实验；现有材料不足以断言“英文就是错因”或“中文一定更好”。不要同时改一长串变量后把收益全部归给语言。

提交阶段模板的候选方向（不是已经验证更高分的版本）：

```text
本轮阶段：提交答案。不再调用工具，不输出 command。
唯一允许的外层格式：{"answer":"字符串"}。
answer 内部严格服从本题要求的答案格式，不附解释。
只使用下面已有来源的证据，不编造未知字段。
如输出格式要求 JSON 对象，先将该对象序列化为 answer 字符串。

本题答案格式：<程序确认的 schema 或题目原文片段>
已有证据：<字段、数值、来源>
可提交的候选答案：<已通过本地格式检查的候选，没有则明确无>
缺失信息：<未证实字段及题目规定的缺失处理>
```

格式修复模板则应只包含：无效原文、具体错误、目标格式示例，以及“不要重新探索，只修控制结构”。探索模板只给下一步需要的文档、现状与回合预算。

赛事公开接口只有 prompt 字符串等顶层字段，没有这里可直接配置的 response_format/tool schema 参数；改进应在当前协议内完成。除非官方另有支持，不要凭空添加 API 参数。

## 7. 可观测性与下一轮验收

源码日志明确只保留元数据，不保存任务答案、动态物品名、prompt 或沙盒命令。因此：目前能定位格式/状态/时间损失，不能逐题判断推理错误或字段语义错误。

建议在符合赛事数据要求的内部受控环境中建立单独任务审计文件：对局与任务实例、回合、阶段、prompt 模板版本、实际 prompt、llmResp、解析结果/具体原因、选定命令、工具输出、候选与提交答案、动作合法性、错误码和判题明确信息。普通 INFO 日志只存元数据与摘要。凭证、个人信息等脱敏；不要把原始内部材料自动提交公开仓库。摘要/哈希不能代替内部保留的原文证据。

验收指标需要分开：JSON 合法率、最终阶段答案比例、无提交超时率、字段通过率、命令失败/无效重试、完成回合与实际奖励。同题或可复现等价实例、同模型设置下对比，避免不同地图与不同任务带来的混淆。

用历史响应做回放可以验证解析器和状态机，但不能证明新 prompt 会让实际模型产生更好的回答；后者必须重新运行模型。当前不存在可用的真实调用原文或本地赛方模型，因此本次没有给出 prompt 改造后准确率/胜率。
