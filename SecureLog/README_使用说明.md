# AgentRace 日志加密工具包：路线 B

版本：ASL1 / 2026-09-15。

**目的：比赛平台不增加任何 Python 包，仍然仅上传一个普通的 `main3.py`，仍然由平台注入端口启动；自己的诊断输出变成密文，下载后在本地恢复。**

本包完成的是“日志组件 + 本地密钥工具 + 本地单文件构建器 + 本地解密器”，**不是已合并到你完整仓库的参赛版本**。构建器读取你电脑上的当前 `main3.py`，输出一个新文件，不覆盖原文件，也不改业务 HTTP 响应或任务脚本字符串。

## 1. 先明确运行在哪里

| 步骤                 | 在哪里运行       | 需要什么                                                           |
| -------------------- | ---------------- | ------------------------------------------------------------------ |
| 生成公钥、私钥       | 你自己的受控电脑 | `rsa==4.9` 和其 `pyasn1` 依赖，或者本地已有的 `cryptography` |
| 生成加密日志版单文件 | 你的电脑         | 本工具包、原始源码、`public.json`；构建步骤本身只用标准库        |
| 比赛运行             | 平台容器         | **生成的单个 Python 文件；日志组件只依赖标准库**             |
| 下载日志后解密       | 你的电脑         | 本工具包、自己的`private.pem`、下载日志、本地密钥后端            |

不要到比赛端生成密钥：你无法取回容器文件，且私钥不应进入对手可下载的日志。

工具包不含你应当使用的私钥，也不预置“大家共用的密码”。测试中的临时密钥在临时目录生成，未打包。

## 2. 最少操作：三条命令

下面假设目录摆放如下。密钥目录请放在代码仓以外的受控位置；示例的几个目录相互并列，不要把整个上层目录提交到 Git。

```text
工作目录/
├── AgentRace/                    # 你的代码仓
│   └── main3.py                  # 要合入日志保护的原始普通单文件
├── AgentRace_SecureLog_B/         # 本工具包；终端当前目录放在这里
│   ├── log_tool.py
│   └── securelog_runtime.py
├── AgentRace_LogKeys/            # 第一步生成；不要上传或提交 Git
├── AgentRace_Submission/         # 第二步生成；只上传其中的 main3.py
└── downloaded_logs/              # 第三步读取下载的日志
```

如果你的原文件实际是 `AgentRace/src/main3.py`，只调整第二条命令的 `--source` 路径。Windows 的 Python 通常也可识别示例里的正斜杠；路径包含空格时使用双引号。WSL/Linux 上命令名是 `python3` 的，将三条命令开头的 `python` 换成 `python3` 即可。

### 第一步：只在本地生成一次密钥

在解压后的工具目录执行：

```bash
python log_tool.py keygen --out AgentRace_LogKeys --bits 3072 --backend rsa
```

`keygen` 是生成密钥命令；`--out` 是一个尚不存在的保存目录；`--bits 3072` 指 RSA 模数长度为 3072 位；`--backend rsa` 指定使用你本地的 `rsa` 包。

生成结果：

```text
AgentRace_LogKeys/
├── private.pem    # 私钥：只在自己的受控电脑和安全备份中保存
├── public.pem     # 公钥：标准 PEM 形式，方便其他工具识别
└── public.json    # 同一公钥的 n/e 和指纹，给构建器读取
```

工具会验证新密钥能够解开 OAEP 封装的测试密钥，并做一条中文诊断的完整加密、分片、还原自检。成功摘要包含 `oaep_and_log_roundtrip_selfcheck: true`。保存或自检失败会以非零状态退出，不应继续构建提交。

**不要每次修改策略都重新生成密钥。**用同一个公钥重新构建新版本，便可继续使用对应私钥解密。换新密钥时使用新目录，并保留旧私钥，否则历史日志可能无法恢复。目录已存在时工具拒绝覆盖。

这里的 `private.pem` **没有口令加密**。POSIX 系统新密钥目录使用 `0700`，私钥文件使用 `0600`；Windows 上这不等于可靠的 ACL，仍需限制目录访问权限。不要将私钥上传到聊天、Git、比赛平台，也不要直接 `print(private_key)`。私钥遗失不能通过公钥补回。

平台包列表不代表你的个人电脑也有相同包。若本地缺少 `rsa`，可以只在自己的电脑安装 `rsa==4.9`（pip 会处理其依赖），**不是给比赛平台装包**：

```bash
python -m pip install "rsa==4.9"
```

若本地已经有 `cryptography`，也可以把第一、第三步的 `--backend rsa` 改为 `--backend cryptography`。这只影响本地密钥读写，生成的比赛程序仍然没有第三方依赖，也不会联网下载代码。

### 第二步：生成一个新的参赛单文件

```bash
python log_tool.py build --source AgentRace/main3.py --public AgentRace_LogKeys/public.json --out AgentRace_Submission/main3.py
```

参数含义：`--source` 为本地原始源码；`--public` 必须是第一步的 `public.json`；`--out` 为新的参赛文件路径。构建不需要私钥。

输出 `main3.py` 和 `main3.py.build.json`。后者记录原文件、产物 SHA-256，公钥指纹，替换日志调用数量，以及业务语法树检查结果。

**平台只上传 `AgentRace_Submission/main3.py`。不要上传工具包、构建报告、公钥文件或私钥目录。**公钥的公开数字 `n/e` 已经嵌入产物，无须在平台创建文件或设置环境变量；原端口参数和 HTTP 入口保留。

构建器只支持包含顶层 `print_log()`、`write_task_trace()` 的**普通单文件**。它定位这两个函数内部的诊断 `print()`，把调用目标换成加密输出器。任务脚本字符串里的 `print()` 不替换，因为那里可能是在输出答案而不是诊断。

它会拒绝已插入过日志组件的文件、旧的 `exec` 动态打包文件、检测到的私钥内容、未审视的其他直接打印出口、部分动态执行与日志框架。遇到“日志出口需人工复核”时，不要绕过检查或批量替换所有 `print()`；保留原文件，按报告定位对应出口。

静态检查是防误接线措施，不是“任何动态代码都不可能漏日志”的证明。应用异常、第三方内部日志、额外子进程输出及平台自己的 HTTP/命令回显也必须单独审查。

### 第三步：下载后在本地解密

```bash
python log_tool.py decrypt --private ../AgentRace_LogKeys/private.pem --input ../downloaded_logs/game.log --out ../downloaded_logs/game_decrypted.log --backend rsa
```

`--private` 是自己的私钥路径；`--input` 是平台下载的密文日志；`--out` 是还原文本的新路径。不要把输入和输出放在同一文件，已有输出不会覆盖。

输出：

```text
game_decrypted.log
game_decrypted.log.report.json
```

还原内容保留原诊断格式，包括原来的 `[函数名]`、`[shadow_turn]` 和 `REPLAY3` 行。之后可以把还原日志交给原复盘工具。平台额外加的时间戳前缀会被解析器忽略，不会复原为原应用输出的一部分。

退出状态：`0` 表示已接收记录的校验与恢复没有发现问题；`2` 表示有缺片、损坏、缺号、运行时丢弃等，仍保存成功还原的部分；`1` 表示路径、私钥、依赖等致命错误。无受信任的结束计数，所以即便退出 `0`，也**不能证明日志末尾完全没有被平台截断**。混合其他公钥记录会计入 `foreign_key_records`，不代表本密钥被破解。

## 3. 现成 `rsa` 包究竟用在哪里

核心密钥生成是以下四行（这是 API 说明，不是完整保存工具）：

```python
import rsa
public_key, private_key = rsa.newkeys(3072, exponent=65537)
public_pem = public_key.save_pkcs1("PEM")
private_pem = private_key.save_pkcs1("PEM")
```

第一行导入 `rsa` 包。第二行返回一对对应的公钥、私钥；3072 指模数位数，65537 是公开指数，不是密码；`public_key` 是可公开的锁，`private_key` 是解锁秘密。

第三行把公钥序列化为 PEM 字节，尚未写入文件。第四行同样得到私钥 PEM 字节，**没有自动给私钥加口令**，不得打印。实际 `keygen` 会用不覆盖原文件的方式保存，并自检。

`save_pkcs1()` 的 PKCS#1 这里描述**密钥存储格式**，不能据此判断数据采用哪一种加密填充。生成的是普通 RSA 密钥对，可用于合适的 OAEP 实现；但 `rsa.encrypt()` 不是 OAEP。

本工具不调用 `rsa.encrypt()` 来加密整份日志，也不把 RSA 切块作为大文件方案。平台使用嵌入的公钥 `n/e` 与 OAEP 编码，只封装随机 32 字节日志密钥；日志正文使用内嵌 ChaCha20-Poly1305。本地 `rsa` 后端借助 `PrivateKey.blinded_decrypt()` 完成私钥运算，再执行 OAEP 解码；这不是在平台提供解密接口。

## 4. 实际采用的密码与日志结构

```text
本地：rsa 生成密钥对
  公钥数字 → 嵌入新的 main3.py
  私钥文件 → 留在自己的电脑

比赛进程：
  安全随机日志密钥 → RSA-OAEP(SHA-256)封装
  一条原始诊断 → 独立压缩/填充 → ChaCha20-Poly1305 → Base64分片 → print(flush=True)

本地：
  平台日志 → 组装密文片段 → 私钥解开日志密钥
  → 验证认证标签 → 解密/解压 → 原诊断文本
```

不是前面设想的 AES-GCM，而是标准 RFC 8439 的 ChaCha20-Poly1305，便于在约束下用较短的纯 Python 源码实现。OAEP 依 RFC 8017。**这是本次写出的标准算法实现，不是搬入一个已经独立审计的成熟加密库。**

每条记录都带被公钥封装的日志密钥，避免第一行丢失导致整场不可恢复。会话内递增序号分配有锁，日志失败也不复用已消费的序号；nonce 来自这个序号而不是游戏回合号；进程重启、fork 或序号用尽重建会话。两条同回合日志也不会重复使用同一密钥下的 nonce。

每条原始诊断单独封装，既保持原日志格式，也便于缺片恢复。正文填充到 256 字节整数倍，但仍泄露粗略长度、数量、时序，不是流量匿名化。恢复器按会话分组、按加密序号排序；不同进程交织的日志不保证恢复原先的全局时间交织顺序。

当前实现仍在加密前保留原诊断内容，不自动识别口令或令牌字段。接入方应先减少不必要的凭据日志；加密不是记录一切秘密的许可。

本次：**41 项测试，40 通过、1 跳过**。详情见 `TEST_REPORT.json`、`TEST_RUN.txt`。涵盖 RFC 向量、120 组 ChaCha20-Poly1305 跨库比较、OAEP 跨库验证、真实 fork、并发、断片、乱序、重复、错误密钥、损坏、失败不回退明文、单文件无第三方依赖启动、构建前后业务语法树与任务脚本字符串检查。

**本次环境无 `rsa`，且无法联网安装，所以真实 `rsa==4.9` 后端测试跳过，不属于已通过项。**所用接口已按官方 4.9 源码核对。跨库验证和本地工具闭环在已安装的 `cryptography 46.0.4` 上执行；你运行第一步 `--backend rsa` 时会自动用你本地真实包进行新密钥与日志恢复自检。

运行 Python 是 3.13.5，另用 AST 检查 Python 3.11 语法；没有在官方容器执行。接入测试是两个日志出口的测试夹具，不是用户完整仓库、真实比赛或策略胜率验收。未做独立安全审计，也不保证 Python 密码运算恒定时间。

本机微基准（RSA-3072，内存计数输出，不含平台 `print/flush`）：

| 输入                      | 稳态中位耗时 |              密文输出 |
| ------------------------- | -----------: | --------------------: |
| 1500 字符随机 Base64 文本 |    约 1.8 ms |    约 2431 字符、2 行 |
| 16 KiB 不可压缩数据       |   约 22.5 ms | 约 23.9 千字符、17 行 |

**不可把这些时间当成平台耗时承诺。**每条原有 `print` 单独加密会产生公钥密钥包与填充开销；大量短日志会膨胀，原 `REPLAY3` 分片也会再分片。必须关注平台日志额度、截断和回合耗时。同步输出遇到阻塞时不能靠异常处理强制限时。

测试命令（本地执行）：

```bash

```

只有 `rsa` 而无 `cryptography` 的电脑，会跳过跨库测试，但运行 RFC 标准向量与真实 `rsa` 后端测试；不需要因此给平台增加任何包。

## 6. 安全边界

这只能保护接入出口之后的自有诊断正文，不会让对局行为或策略源码不可观察，也不能收回已经下载的明文。如果平台把 `executeCmd`、HTTP 响应、任务 stdout 或 stderr 另行公开，这些副本不受本组件保护；不能为了隐藏日志把判题器需要的业务数据也改成密文。

认证标签能检测不知道日志密钥的人对既有记录的修改，但**公钥加密不是发送者签名**：拿到公钥的人也能创建另一份可解密的伪造会话。请从可信平台导出日志，不把解密成功当作来源真实性证明；没有全日志删除/尾部截断证明。

公钥封装不提供前向保密：长期私钥泄露后，持有历史密文的人也可能恢复历史日志。能够读比赛进程内存的管理员或攻击者可取得当时的日志密钥；本方案不对抗这类权限。

加密/打印失败时不输出原文，只限频输出固定 `SECURE_LOG_DROPPED`，或在 stdout 已损坏时静默丢弃。业务逻辑不应依赖日志成功与否。不过源码导入错误、日志组件初始化之前的故障，以及其他未接管输出路径不在这个保证内。

**建议先用生成版本进行一次平台实测，核对解密后的诊断连续性、日志额度和回合耗时，再据此决定正式使用。**
