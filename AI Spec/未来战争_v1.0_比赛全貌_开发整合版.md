# 0. 一句话理解这场比赛

这是一个 **1300 回合、昼夜交替、双方同时行动的回合制策略游戏**，同时叠加了：

1. 地图寻路与多角色调度；
2. 采矿、卖矿、买道具、建筑升级的经济系统；
3. 夜间机器人防守与武器火力调度；
4. 部分可观测的敌方信息；
5. 世界新闻驱动的资源价格/资源可采集性推理；
6. 跨多天累积民间传闻的隐藏宝藏推理；
7. 需要调用 LLM、执行沙盒命令并形成 SOP/SKILL 的“自进化任务”；
8. HTTP 请求/响应式判题接口；
9. 极严格的异常次数限制：**累计 5 次代码异常后，该队后续回合不再调度**。

因此，程序不能只写成一堆 `if/else`。正确的开发方向是：

```text
HTTP 接口
   ↓
输入容错解析
   ↓
持久化世界状态 / 历史记忆
   ↓
上一回合结果回收
   ↓
阶段识别（日/夜/任务/宝藏）
   ↓
多个子规划器产生候选动作
   ↓
动作冲突消解 + 合法性校验
   ↓
构造稳定 JSON Response
```

# 2. 比赛总体结构

## 2.1 对局

**[明确规则]**

- 每场比赛由两支队伍对战。
- 无先后手，双方每回合同时调度。
- 每场比赛分上半场和下半场。
- 下半场双方互换位置。
- 单半场最多 10 天，即 1300 回合。
- 两方基地位于地图左上区域和右下区域。

游戏目标不是单纯“杀机器人”，而是：

```text
白天：
采矿 → 卖矿 → 获得金币
     → 买升级券 / 消耗品 / 召唤令 / 任务用品
     → 建造与升级
     → 开拓者做任务
     → 解析新闻和宝藏线索
     → 为夜间提前站位

夜晚：
机器人出现
     → 角色操控最多 3 座武器工事
     → 防守己方基地
     → 可用炸弹/眩晕等道具
     → 对方也可能通过机器人召唤令增强我方夜袭压力
```

# 6. 距离、移动、邻接

## 6.1 所有距离使用切比雪夫距离

**[明确规则]**

```text
dist((x0,y0),(x1,y1))
= max(abs(x1-x0), abs(y1-y0))
```

因此“周围一格”就是 8 邻域。

例如角色在 `(10,10)`，一格内包括：

```text
(9,11)  (10,11)  (11,11)
(9,10)  [10,10]  (11,10)
(9,9)   (10,9)   (11,9)
```

## 6.2 移动

角色每回合最多移动 1 格，可以走 8 个方向：

```text
↖ ↑ ↗
← X →
↙ ↓ ↘
```

**[图转文本]** PDF 特别说明：两个障碍物即使卡在斜向路径两边，也不禁止对角通行。

例如：

```text
# # .
. P .
. . .
```

只要斜对角目标格本身可进入，允许角色斜走；不存在常见 A* 中的“禁止穿角”规则。

因此路径算法应使用：

```text
8 邻接
切比雪夫启发函数
允许 diagonal corner cutting
```

# 7. 移动碰撞

## 7.1 碰撞触发

**[明确规则]**

角色移动可能因以下情况失败：

### 目标点受阻

目标位置：

```text
有障碍物
或
被本回合没有移动的其他角色占据
或
被机器人占据
```

### 目标点争夺

多个角色/机器人计划去同一个位置。

### 位置互换

例如：

```text
A 当前在 (1,1)，计划去 (2,1)
B 当前在 (2,1)，计划去 (1,1)
```

双方不能互换。

## 7.2 碰撞结果

```text
角色 vs 角色：
双方均不移动

角色 vs 障碍物：
移动角色不移动

角色 vs 机器人：
双方均不移动
```

**[工程建议]**

己方两个工人和开拓者的移动计划应先做一次 reservation：

```text
reserved_target_cells
planned_edges
```

至少避免：

```text
己方角色抢同一目标格
己方角色互换位置
移动到己方未移动角色当前格
```

机器人和隐藏敌人仍可能导致不可预测碰撞，因此每回合重新规划。

# 13. 武器控制与攻击

## 13.1 武器不会自动攻击

三种武器都需要角色操控。

操控者必须站在武器周围一格内。

攻击命令里：

```json
{
  "action": "attack",
  "controllerId": "10010",
  "targetPos": [...]
}
```

而 `roleCommandMap` 的 key 在样例中是武器 ID：

```text
weapon_id -> attack command
controllerId -> 操控它的 worker/pioneer ID
```

## 13.2 一名角色只能同时操控一座武器

接口明确：

```text
一个角色只能同时操控一座武器工事
```

**[待确认]** 操控武器是否同时占用该角色自己的“本回合动作”存在协议表达上的歧义：攻击命令挂在武器 ID 上，但任务书又强调每个角色每回合只能一个动作。

**[工程建议]** 在未实测前使用保守策略：

```text
如果 character 被用作 controllerId：
本回合不要再给该 character 下 move/buy/use/... 指令
```

这样最不容易触发非法动作。

## 13.3 只有夜晚可以攻击

白天发送 `attack` 非法。

# 14. 攻击距离 —— 图片转文本

距离是切比雪夫距离。

例如攻击距离 `R = 4`：

```text
所有满足

max(abs(dx), abs(dy)) <= 4

的格子都在射程内。
```

即攻击区域是边长 9 的方形，而不是圆。

# 15. 加特林炮台

## 15.1 基本机制

等级决定同回合子弹数量：

```text
L1：1 发
L2：2 发
L3：3 发
```

每发：

```text
10 伤害
```

`targetPos` 数量必须等于武器当前等级。

## 15.2 90° 锥形限制

多个攻击目标必须处于同一个 90° 锥形内：

```text
任意两个目标相对于加特林方向的夹角 <= 90°
```

否则：

```text
整次攻击非法
```

这不是“某一颗子弹失效”，而是整组攻击非法，因此必须在返回前检查。

## 15.3 弹道

每颗子弹沿：

```text
武器坐标中心
→
指定 targetPos 坐标中心
```

的直线飞行。

子弹碰到该弹道上最近的一台机器人时：

```text
立即命中
子弹消耗
造成 10 伤害
```

因此加特林不是“targetPos 上有什么就打什么”，而更像指定一条射线/弹道。

# 16. 电磁狙击炮

始终只提供：

```text
1 个 targetPos
```

升级增加电磁能量：

```text
L1：10
L2：20
L3：30
```

攻击沿直线穿透。

路径上的存活机器人依次受到：

```text
damage = min(remaining_energy, robot.current_health)
```

然后：

```text
remaining_energy -= damage
```

直到：

```text
能量耗尽
或
到达指定终点
```

**策略意义：**

# 30. `summonTreasure` 的高风险规则

命令：

```json
{
  "action": "summonTreasure",
  "targetPos": [{"x": 1, "y": 2}],
  "item": ["AcientTablet", "StarSand"]
}
```

## 30.1 动作合法条件

至少包括：

```text
targetPos 在 pioneer 周围一格
item 中每件物品都真实存在于 pioneer 背包
```

不满足：

```text
动作非法
物品不消耗
```

## 30.2 一旦动作本身合法

无论最终是否成功打开：

```text
任务用品都会被消耗
```

这是非常重要的资源风险。

## 30.3 上回合结果码

`lastSummonTreasureResult`：

```text
0 = 未探测
    上回合没发 summonTreasure
    或动作非法

1 = 成功获得宝藏

2 = 无宝藏 / 宝藏还没到开放时间

3 = 献祭物品集合错误
    不能多
    不能少
    顺序不限

4 = 宝藏已空
```

因此：

```text
不能靠暴力穷举位置/时间/物品组合
```

因为只要动作合法但猜错，物品就会被吃掉。

# 31. 自进化任务

这是本比赛最“Agent”化的部分。

## 31.1 任务点

地图有 4 个团队专属任务点：

```text
Challenger：
- challengerTaskPoint1
- challengerTaskPoint2

Defender：
- defenderTaskPoint1
- defenderTaskPoint2
```

每队只能用自己的任务点。

其中 TaskPoint2：

```text
占 2 个地图格
```

Request 样例中也体现为同一种 `neutralType` 出现两个坐标。

因此寻路/邻接判断不能只依赖 `PlayerTask.taskPosition`，最好同时从 `mapInfo.zones` 找出该任务点所有占格。

## 31.2 接任务

只有：

```text
pioneer
```

可 `acceptTask`。

必须站在：

```text
己方任务点周围一格
```

## 31.3 任务状态字段

`teamOur.playerTasks[]`：

```text
taskType
taskPosition
coldDownRounds
scoreReward
goldReward
isValid
timeoutRounds
```

其中：

```text
coldDownRounds = 0
→ 当前没有刷新冷却

isValid = true
→ 当前允许领取
```

完成/结束后任务点：

```text
30 回合刷新
```

任务总数有上限，因此最终可能永久 `isValid=false`。

## 31.4 任务什么时候强制结束

以下任一发生：

```text
任务完成
超过 timeoutRounds
pioneer 离开己方任务点周围一格
领取任务的 pioneer 死亡
```

所以一旦接任务：

```text
不要让 pioneer 被普通日间调度器随便移动走
```

应由 TaskPlanner 独占控制 pioneer。

# 33. LLM 调用接口

Response 顶层：

```json
"prompt": "..."
```

系统把它提交给 LLM。

下回合 Request：

```json
"llmResp": "..."
```

带回上回合 LLM 响应。

因此 LLM 是明显的“跨回合异步接口”：

```text
Round r:
发送 prompt

Round r+1:
读取 llmResp
```

代码不能写成当前函数里同步等待 LLM。

# 34. LLM 调用额度

## 34.1 普通游戏阶段

每个游戏日：

```text
最多 3 次 LLM 调用
```

在当天第一个回合重置。

超出：

```text
errorCode = 5
LLM额度超限
```

## 34.2 自进化任务期间

从接取任务到任务结束：

```text
LLM 调用不受 3 次/日限制
并且
不计入当日 3 次额度
```

**[工程建议]**

维护：

```text
llm_calls_today
llm_request_pending
last_prompt
last_llm_response
```

防止在普通阶段无意义消耗额度。

**[待确认]**

# 35. `executeCmd` 沙盒

Response 顶层：

```json
"executeCmd": "python xxx.py"
```

只有在：

```text
自进化任务执行期间
```

才能使用。

## 35.1 沙盒能力

```text
可执行基础 shell 命令
可执行 Python
不能访问外部网络
```

沙盒环境与比赛编译运行环境一致。

## 35.2 超时

单条命令：

```text
不得超过 15 秒
```

超时不会算队伍异常次数。

沙盒故障也不会算队伍异常次数。

## 35.3 返回结果

下一回合：

```text
lastCmdResult
```

格式：

```text
正常：
[exitCode:N]
<输出>

超时：
[TIMEOUT]
<部分输出>

判题器异常：
[JUDGER_ERROR]
<原因>

输出超过 64KB：
末尾追加
[TRUNCATED]
```

因此 Command Task 的天然循环是：

```text
phaseTask
   ↓
LLM 规划
   ↓
executeCmd 探索
   ↓
下回合 lastCmdResult
   ↓
LLM 分析
   ↓
必要时继续 executeCmd
   ↓
submitAnswer
```

**[工程建议]**

```text
  │
  ├─ 找可接任务

  │
```


# 38. 任务积分

总积分：

```text
totalScore = score1 + score2 + score3
```

## 38.1 完整完成任务

```text
score1 =
任务积分奖励
+
5 × 任务标准回合数 / (实际完成回合 - 接取回合)
```

其中：

```text
任务标准回合数 = timeoutRounds
```

即：

```text
越快完成，速度奖励越高
```

如果：

```text
timeoutRounds = T
完成耗时 = d
```

速度奖励为：

```text
5T / d
```

因此任务速度不是小优化，而可能非常值钱。

## 38.2 部分完成

```text
score1 = 任务积分奖励 × 通过率
```

```text
通过率
= 正确字段个数 / 全量字段个数
```

部分完成没有写速度奖励。

## 38.3 任务金币

任务结束后：

```text
获得金币
= goldReward × 通过率
```

# 40. 生存积分

每天：

```text
10 × day × 存活系数
```

如果基地当天已摧毁：

```text
当天及以后存活系数 = 0
```

如果 10 天全部存活：

```text
10 × (1+2+...+10)
= 10 × 55
= 550
```

也就是说纯生存最高提供：

```text
550 分
```

这也是为什么基地存活必须是高优先级目标。

# 41. 胜负判定

## 41.1 半场结束条件

至少包括：

```text
双方异常响应都达到 5 次
1300 回合结束
双方基地都被完全摧毁
```

注意：

```text
单队异常达到 5 次
≠ 比赛立即结束

而是：
该队后续代码不再被调度
```

如果两队都达到 5 次，才满足对应的比赛结束条件。

## 41.2 基地毁灭优先性

# 43. Python SDK 官方骨架

当前上传的 `main3.py` 本质如下：

```python
import sys

from flask import Flask, request, jsonify

sys.stdout = open(sys.stdout.fileno(), mode='w', encoding='utf-8', buffering=1)
sys.stderr = open(sys.stderr.fileno(), mode='w', encoding='utf-8', buffering=1)

app = Flask(__name__)


@app.route('/', methods=['POST'])
def process_request():
    data = request.get_json()
    command = callback(data)
    resp = jsonify(command)
    return resp


def callback(json_data):
    # 选手代码
    res = json_data
    return res


if __name__ == '__main__':
    app.run(port=int(sys.argv[1]))
```

## 43.1 这段骨架现在并不能参赛

因为：

```python
res = json_data
return res
```

只是把 Request 原样返回。

而判题器需要的是：

```json
{
  "roleCommandMap": {},
  "prompt": "",
  "executeCmd": ""
}
```

因此第一件事就是重写 `callback`。

## 43.2 `0.0.0.0` 监听问题

接口文档写：

```text
ip 地址均为 0.0.0.0
```

但 Flask：

```python
app.run(port=...)
```

默认没有显式 `host="0.0.0.0"`。

**[工程建议]**

为了与文字协议一致，可考虑：

```python
app.run(host="0.0.0.0", port=int(sys.argv[1]))
```

但应先做一次平台启动验证。

# 60. 官方 `response.txt` 不能直接当 JSON 模板

这是最需要提醒后续 Codex 的一点。

提供的 `response.txt`：

1. 在同一个 JSON object 里重复 `"10010"`、`"10011"`、`"10012"` 多次。
2. JSON 重复 key 即使某些解析器接受，也只会保留最后一个值。
3. `summonTreasure` 示例的 `targetPos` 后面缺少一个逗号，再接 `"item"`，因此文件本身甚至不是严格合法 JSON。
4. 接口文档已经明确解释：这些重复角色 ID 只是为了“把所有动作变体列一遍”，**不是同一回合能给一个角色下多条命令**。

所以绝对不要：

```text
复制 response.txt
→ 改几个坐标
→ 直接发送
```

必须自己构造合法字典。

# 63. “异常”与“动作执行失败”必须区分

## 63.1 会计入异常的典型问题

例如：

```text
move 缺 targetPos
attack 缺 targetPos
Bomb 缺 targetPos
DizzyWeapon 缺 targetPos
action 拼错
JSON 格式错
HTTP 超时
```

## 63.2 不计异常的执行失败

动作字段合法，但游戏结算失败，例如：

```text
移动碰撞
攻击落点无目标
```

这种：

```text
该动作失效
但不累计队伍异常
```

所以程序的目标不是“每条动作必定成功”，而是：

```text
每一条发出去的动作必须格式正确、类型正确、基本规则合法
```

# 69. 日间寻路

地图只有：

```text
41 × 32 = 1312 格
```

规模很小。

标准库 A*/BFS 足够。

建议：

```text
8 邻接
Chebyshev heuristic
动态障碍表
每回合重规划
```

目标往往不是进入设施格，而是：

```text

```

因此通用接口应是：

```text
find_best_adjacent_cell(target_cells)
```

而不是：

```text
path_to(target_pos)
```

因为：

```text
vendor
weaponShop
mine
taskPoint
building
```

本身都是障碍或不可站。

# 70. 多角色路径冲突

两个 worker 常会同时工作。

如果单独跑 A*：


合在同一回合可能：


所以动作生成后应做：


典型规则：

```text

高优角色保留目标格
低优角色重新选邻格/等待
```

# 76. ActionValidator 应该做什么

建议所有动作在出门前经过统一校验。

例如：

```text

- targetPos 长度 == 1
- Chebyshev 距离 == 1
- 在地图内
- 目标当前不是已知静态障碍

attack:

- weapon.cooldown == 0

- actor 是 worker
- target 是矿
- actor 距矿 <=1

build:
- actor 是 worker
- 白天
- target 距 actor <=1
- target 位于对应建造区
```

# 77. HTTP 稳定性建议

因为 5 次异常就基本出局，入口必须有最后保险。

建议结构：

```python
def process_request():
    try:
        data = request.get_json()
        command = callback(data)
        command = ensure_valid_response(command)
        return jsonify(command)
    except Exception as exc:
        print(f"[process_request] unexpected error: {exc}")
        return jsonify({
            "roleCommandMap": {},
            "prompt": "",
            "executeCmd": "",
        })
```

这样至少内部策略异常时：

```text
本回合什么也不做
```

优于：

```text
HTTP 500
```

所有日志建议按统一格式：

```text
[函数名] 日志信息
```

例如：

```text
[callback] round=85 phase=night
[plan_worker] role=10010 target=(4,24)
[validate_action] reject illegal gatling cone
```

# 78. 性能预算

HTTP 连接建立后：

```text
5 秒内必须返回 Response
```

因此 `callback` 不应执行：

```text
大型搜索
死循环
本地 LLM
同步等待外部资源
```

地图只有 1312 格，合理的：

```text
BFS
A*
候选枚举
简单组合优化
```

都应远小于 5 秒。

沙盒 `executeCmd` 的 15 秒限制是判题器执行命令的限制，不应和 callback 自身 5 秒响应预算混淆。

# 86. 最后的全局认知

从比赛设计看，真正需要实现的不是一个单独算法，而是一个 **有限回合、多 Agent、多目标、部分可观测、带语言推理与工具调用的游戏 Agent**。

可以把整个系统抽象为：

```text
State_t
  =
地图
+ 我方状态
+ 当前可见敌方
+ 全图机器人
+ 经济
+ 商店
+ 新闻
+ 任务
+ LLM结果
+ Shell结果
+ 历史记忆

Policy(State_t, Memory)
  ↓
Actions_t
  =
角色动作集合
+ 可选 LLM Prompt
+ 可选 executeCmd

Environment
  ↓
State_(t+1)
```

而 Memory 不只是锦上添花，它直接关系到：

```text
跨天 folkLegends
新闻效果持续时间
矿刷新
上回合动作结果
LLM 异步响应
沙盒异步响应
自进化 Skill
敌方 last-seen
任务最好答案
```

因此建议从第一版代码就把“跨回合状态”作为一等公民，而不是最后再补。

# 87. 当前最值得优先向官方答疑确认的问题

按开发阻塞程度排序：

```text
1. 围墙 build 每次具体消耗多少 stone？
2. 武器 build 的 name 精确值是否就是 gatling / railgun / rocket？
3. controller 操控武器后，该 worker/pioneer 同回合还能否执行自己的其他动作？
4. roundNo 从 0 还是 1 开始？
5. station.pos=左上角时，2×2 实际占格坐标如何定义？
6. 加特林/电磁炮弹道经过格子的精确离散算法是什么？
7. 武器攻击是否能伤害敌方角色/建筑，还是只伤机器人？
8. collect/sell/buy/remove/use 是否允许夜间执行？目前只有 build 和 attack 有明确昼夜限制。
9. 自进化任务错误 submitAnswer 后任务是否继续？能否多次提交直到正确/超时？
10. 自进化 sandbox 在多个回合的 executeCmd 之间文件是否持久化？
11. Python 允许的 pip/第三方库完整清单是什么？
12. 下半场是否重启选手进程？若不重启，roundNo 是否重置？
```

把这 12 个问题确认后，绝大多数协议级不确定性都可以消除。
